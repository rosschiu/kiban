# Kiban on Kubernetes

This directory is the Kubernetes translation of `infra/compose.yaml`: the same 9 app services,
Postgres, Keycloak, the `migrate`/`bootstrap` one-shot jobs and the gateway edge, expressed as
[Kustomize](https://kubectl.docs.kubernetes.io/references/kustomize/) manifests instead of a
compose file. Nothing in the platform assumes Compose. The manifest set has been brought up end
to end on a local [kind](https://kind.sigs.k8s.io/) cluster. It has **not** been run against a
real (non-kind) cluster yet. Review every placeholder before you use it.

## Why Kustomize, not Helm

Kustomize needs no templating language, no chart conventions, and no CLI beyond `kubectl`
(`kubectl apply -k` / `kubectl kustomize` have been built in since 1.14). Every manifest here is
plain YAML, and overlays patch it with structured JSON patches, not string templates. The
deployment surface is small: one namespace, and one environment shape with a handful of
differences between kind and production. That doesn't need Helm's templating or its
release/rollback machinery, because `kubectl rollout undo` and `kubectl apply -k` cover it.
Revisit this if a second, meaningfully different deployment shape (for example a multi-tenant
chart for third-party operators) makes templating worth it.

## Layout

```
deploy/k8s/
  base/                    # the full 12-workload manifest set, image tags = :latest placeholders
    namespace.yaml
    configmap.yaml          # non-secret env (kiban-config) + postgres keycloak-DB init SQL
    secret.example.yaml     # COMMITTED placeholder — field list only, never real values
    secret.yaml              # gitignored — generated by gen-secrets.sh, required to `apply -k`
    postgres.yaml            # StatefulSet + headless Service + PVC (volumeClaimTemplates)
    keycloak.yaml             # Deployment + Service (kiban-keycloak image — MFA authenticator + realm)
    jobs.yaml                  # migrate, bootstrap — plain one-shot Jobs
    template/service.yaml      # the one Deployment + Service shape every app service is cut from
    registry/, identity/, org/, authz/, notification/, timesheet/, docs/, helpdesk/, gateway/
                               # one kustomization.yaml each: `template/` + JSON patches for that
                               # service's name, image, port and env (parity with infra/compose.yaml)
    ingress.yaml               # class-agnostic Ingress — see "Ingress vs. port-forward" below
  overlays/
    kind/kustomization.yaml    # retags images to :v0.1.0 (or whatever `make images-all
                                # VERSION=...` built), imagePullPolicy: Never (no registry pull)
    production/kustomization.yaml # SAMPLE — GHCR image refs, real domain, cert-manager Ingress
                                    # annotations, a real StorageClass — every value a placeholder
  gen-secrets.sh              # write-once secret generator (same approach as infra/setup.sh)
  apply.sh                    # staged apply + kubectl wait, in compose's own depends_on order
```

## Apply order (and why it's a plain script, not initContainers)

Kubernetes has no native "wait for this Job before that Deployment starts" primitive. There were
two ways to reproduce `infra/compose.yaml`'s `depends_on` chain (postgres -> keycloak -> migrate
-> bootstrap -> the 9 app services):

1. **initContainers on every Deployment** that wait for the upstream dependency (a `busybox`/
   `curl` loop polling the dependency's health, or a Job's completion via the API).
2. **Plain Jobs + `kubectl wait` in the apply script**: apply everything, then gate
   *progression*, not *creation*, on each stage's readiness.

This directory uses (2). It needs no extra images or sidecars, and the ordering logic lives in
one script you can read top to bottom (`apply.sh`). It also matches how the app services already
behave under `docker compose`. Most of them (`notification`/`timesheet`/`docs`/`helpdesk`)
tolerate a temporarily unreachable `authz`/`org` at startup (lazy per-request calls that fail
closed) instead of crash-looping. So having them exist briefly as unready Pods before
`migrate`/`bootstrap` finish is the same startup-race tolerance compose already relies on.

```
deploy/k8s/gen-secrets.sh                       # once, before the first apply
deploy/k8s/apply.sh kind                        # or: production
```

`apply.sh` first deletes any previous `migrate`/`bootstrap` Jobs (a Job's pod template is
immutable, so re-applying one with a new image tag fails, and a leftover completed Job would
pass the wait without running the new migrations — this is what makes the script re-runnable for
an upgrade), runs `kubectl apply -k <overlay>` once for the full manifest set, then waits in
stages: postgres ready -> keycloak ready -> `migrate` Job complete -> `bootstrap` Job complete ->
every app Deployment's rollout finishes. The script's own header explains the reasoning.

## Resource requests/limits

These numbers come from `docker stats --no-stream` against the running compose stack while idle,
with a small demo-seed dataset loaded:

| Service | Measured (idle) | Request | Limit |
|---|---|---|---|
| Go app services (registry/identity/org/authz/notification/timesheet/docs/helpdesk) | 5.7–12.5MiB RSS, ~0% CPU | 32Mi / 10m | 128Mi / 200m |
| gateway | 13.9MiB RSS, ~0% CPU | 32Mi / 20m | 128Mi / 300m |
| keycloak | 810.6MiB RSS, ~9% CPU | 640Mi / 250m | 1024Mi / 1000m |
| postgres | 111.6MiB RSS, ~4.6% CPU | 128Mi / 100m | 512Mi / 500m |
| migrate / bootstrap (one-shot Jobs, not measured: they exit within seconds) | — | 64Mi / 50m | 256Mi / 500m |

Requests sit near or below the measured idle floor, rounded up to a clean number. Limits give
roughly 2–10x headroom for real traffic and import bursts, without letting one runaway workload
starve a small node. These figures describe an idle demo dataset, not a loaded production
workload. Re-measure once you have real traffic.

## Ingress vs. port-forward

`base/ingress.yaml` is class-agnostic: no `ingressClassName`, so it works with whatever controller
a cluster already runs. It routes to the gateway's plain-HTTP `:8090` listener. A real deployment
terminates TLS at the Ingress (see "Production notes" below), the same way
`infra/compose.public.yaml` runs the gateway behind a shared reverse proxy (`KIBAN_TRUSTED_PROXY`).

**kind ships no ingress controller by default.** The kind quickstart below reaches the gateway
through `kubectl port-forward` instead. As a result the Ingress resource's own admission and
routing behavior is untested. Validate it against your cluster's ingress controller before you
rely on it in production.

## kind quickstart

```bash
# 0. install kind + kubectl (both are static binaries; a user-owned bin dir is fine)

# 1. build the images locally (13; kind needs the 12 below — gateway-devcert is compose-only)
#    and load them into the kind cluster (no registry pull)
make images-all VERSION=v0.1.0
kind create cluster --name kiban
for img in kiban-registry kiban-identity kiban-org kiban-authz kiban-notification \
           kiban-timesheet kiban-docs kiban-helpdesk kiban-gateway kiban-migrate \
           kiban-bootstrap kiban-keycloak; do
  kind load docker-image "$img:v0.1.0" --name kiban
done

# 2. secrets, then apply
deploy/k8s/gen-secrets.sh
deploy/k8s/apply.sh kind

# 3. reach the gateway (no Ingress controller on kind — see above)
kubectl -n kiban port-forward svc/gateway 8090:8090
# in another shell: curl http://localhost:8090/ -H "Host: gateway:8090" ...
# (base/configmap.yaml explains why the Host header must match the in-cluster Service name)

# 4. teardown
kind delete cluster --name kiban
docker image rm $(docker images 'kiban-*:v0.1.0' -q)
```

The `v0.1.0` tag must match the `newTag` values in `overlays/kind/kustomization.yaml`.

## Production notes (what a real cluster changes)

- **Storage class**: `base/postgres.yaml`'s `volumeClaimTemplates` sets no `storageClassName`.
  On kind the default dynamic host-path provisioner (`standard`) is used unpatched. A real cluster
  almost certainly wants a block-storage class. `overlays/production`'s patch has a placeholder
  and examples: `gp3` on EKS, `premium-rwo` on GKE, `managed-csi-premium` on AKS.
- **Ingress + TLS**: `overlays/production` pins an `ingressClassName`, a host, a
  `cert-manager.io/cluster-issuer` annotation and a `tls:` block. It does NOT install cert-manager
  or create the `ClusterIssuer` it references. Both are one-time, cluster-level installs; see
  [cert-manager's installation docs](https://cert-manager.io/docs/installation/) and the
  [ACME `ClusterIssuer` guide](https://cert-manager.io/docs/configuration/acme/).
- **External Postgres option**: nothing here requires the in-cluster `postgres` StatefulSet. A
  managed Postgres instance (RDS, Cloud SQL, etc.) works too, because every service reaches
  Postgres through a plain host:port and DSN. To use one, drop `base/postgres.yaml` from the
  overlay (a `patches: - target: {kind: StatefulSet, name: postgres}` with `$patch: delete`, or a
  custom base copy without `postgres.yaml`). Then point the `postgres` Service DNS name at the
  managed instance. An `ExternalName` Service keeps every manifest's `postgres:5432` reference
  unchanged: `kubectl create service externalname postgres --external-name=<managed-host>`.
- **Replica counts**: every Deployment here is `replicas: 1`. The app services are stateless
  HTTP servers with no in-memory session state, so they can scale horizontally without code
  changes. `keycloak` needs its own Infinispan clustering config before it can run more than one
  replica safely. `postgres` is a StatefulSet with no replication configured, which makes it a
  single point of failure; a managed Postgres (above) is the more likely answer on a real
  cluster.
- **Real domain**: `overlays/production` patches a single `kiban-config` ConfigMap
  (`KIBAN_DOMAIN`/`KIBAN_GATEWAY_ORIGIN`/`KEYCLOAK_ISSUER_URL`), and that is the one place to set
  the real hostname. Every token-verifying service reads `KEYCLOAK_ISSUER_URL` from that key
  (see `base/configmap.yaml`'s header). The same overlay pins Keycloak to that origin
  (`KC_HOSTNAME=https://<domain>`, `KC_HOSTNAME_STRICT=true`), exactly as
  `infra/compose.public.yaml` does: the base's `STRICT=false` lets Keycloak derive its issuer and
  self-referencing URLs from `X-Forwarded-Host`, which the gateway (`KIBAN_TRUSTED_PROXY=true`,
  always behind the Ingress here) passes through from whatever reached it — the kind-only
  `Host: gateway:8090` workaround depends on that, production must not. Forwarded headers should
  reach the gateway only from the Ingress controller; that is a NetworkPolicy (next bullet), not
  something the manifests can enforce.
- **Pod hardening**: the nine app images run as uid/gid 65532 with a read-only root filesystem,
  all capabilities dropped, `allowPrivilegeEscalation: false` and the `RuntimeDefault` seccomp
  profile (`base/template/service.yaml`). The `migrate`/`bootstrap` Jobs run the toolchain image
  as root; Postgres and Keycloak keep their upstream images' defaults.
- **NetworkPolicy and PodDisruptionBudget are yours**: nothing here restricts pod-to-pod traffic
  (any pod in the cluster can reach `postgres:5432` and Keycloak's `:8080`/`:9000`), and the
  `replicas: 1` Deployments carry no PDB, so a node drain takes the stack down. Add a
  default-deny NetworkPolicy for the `kiban` namespace that admits only the gateway from the
  Ingress and the app services to Postgres/Keycloak, and PDBs once you run more than one
  replica; both depend on your CNI and topology, which is why they are not shipped here.

## What's proven, what isn't

Proven on kind:
- The full 12-image build, `kind load`, and staged `apply.sh` bring-up.
- A password-grant login through the gateway, `GET /api/platform/capabilities` (200), one module
  API call (200), and `/metrics` reachable in-cluster with `kiban_build_info` carrying the built
  version.
- Clean teardown (`kind delete cluster`, images removed).

Not proven:
- Nothing here has run against a real (non-kind) cluster.
- The Ingress resource's actual admission/routing behavior (no controller on kind — see "Ingress
  vs. port-forward" above).
- Multi-node behavior, real storage-class provisioning, cert-manager/ACME issuance, and horizontal
  scaling beyond `replicas: 1`.

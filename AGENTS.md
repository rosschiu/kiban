# Working in this repository

This file is for coding agents and for people who want the short version. It says what Kiban
is, what to read in which order, which checks to run, and which files never to edit by hand.
Everything here is also in the documentation at <https://rosschiu.github.io/kiban/>.

## What this is

Kiban is a self-hostable identity, organization and authorization foundation for business
applications: Go services, Postgres 18, an embedded Keycloak, a TypeScript SDK and a React
sample shell, run with Docker Compose. Business logic lives in modules built on top; four
sample modules ship in `modules/`. Version 0.1 supports in-tree Go modules only, issues a
backend its own token only through a service client created at bootstrap, and creates
companies only through the org service's internal routes. `docs/limitations.md` is the complete list; read it before promising anything.

## Read in this order

1. `docs/index.md` and `docs/concepts.md`: the model (companies, members, positions, groups,
   relation tuples, modules).
2. `docs/integrate.md`: the step-by-step tracks for a frontend using the SDK, a backend
   becoming a module, and a backend calling the REST API.
3. `docs/building.md`: the module reference (runtime contract, manifest, authorization
   fragment, migrations, the checklist for adding a module).
4. `docs/sdk-guide.md` and `docs/reference.md` when you need a signature or a route.
5. `docs/operating.md` and `docs/security.md` when you deploy.

## Run before you claim anything works

```
make setup && make dev        # the stack, at https://127.0.0.1:8443
make validate-modules         # manifests, fragments, OpenAPI, migrations of every module
make check                    # formatting, vet, tests, coverage, licences, docs, secrets
make test                     # race detector and the authorization harness
make docs-site                # the documentation, strict
```

`make check` and `make test` need Docker; they start an isolated test stack. Run them in the
foreground and read the last lines.

## Rules of the tree

- Never commit `.env`, `.env.test` or anything under `infra/secrets-in/`.
- Never edit by hand: `migrations/*/checksums.json` and `modules/*/migrations/checksums.json`
  (regenerate with `go run ./cmd/modvalidate -write-checksums <dir>`), `coverage/ratchet.json`
  (the ratchet only rises), `docs/api/` and `docs/sdk/` (generated by `make docs`),
  `deploy/quickstart/docker-compose.yml` (generated by `make quickstart-compose`).
- A shipped migration is frozen. Add a new numbered file; never change an existing one.
- Every mutation writes its audit event in the same transaction. Do not add a write path that
  skips it.
- Authorization decisions come from the authorization service. Do not check permissions from
  a claim in the token or from a table of your own.
- A module touches only its own schema and its own base path. The validator rejects the rest.
- Keep the documentation true. If you change behaviour, change the page that describes it in
  the same commit; `make docs-freshness-check` catches the generated parts, you catch the prose.

## Conventions

Go uses the standard library `net/http` and `sqlc`; the SDK is TypeScript with Vitest;
commits are conventional (`feat(scope):`, `fix(scope):`, `docs(scope):`). See
`CONTRIBUTING.md` for the pull-request checklist and `SECURITY.md` for reporting.
